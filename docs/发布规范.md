# 发布规范

> 这份文档定义 PromptPair 的版本、提交、标签、日志、发布流程。
> 目标：**任何一次发布都可以被追溯、被回滚、被自动更新系统正确识别。**
> 规则一旦定下就照做，不靠记忆。

---

## 1. 版本号：语义化版本 2.0.0

格式 `MAJOR.MINOR.PATCH`，例如 `1.4.2`。

| 位 | 什么时候 +1 | 举例 |
| --- | --- | --- |
| **MAJOR** | 有不兼容变更。对本文具来说 = **用户数据需要手动迁移**，或旧库打不开 | 重写存储层、改变库目录结构 |
| **MINOR** | 向下兼容地新增功能 | 新增「提示词变量模板」、新增播放器 |
| **PATCH** | 向下兼容地修缺陷 | 修复导入时标签重复、修卡片错位 |

补充规则：

- `0.x.y` 期间视为开发期，**任何改动都可能破坏兼容**，但仍遵守 `x` 与 `y` 的语义
- 1.0.0 之后再严格按上表
- 预发布版用 `-beta.1`、`-rc.1` 后缀：`1.2.0-beta.1`
- **不要**出现 `1.0`、`v1.0.0.0`、`1.0.0-final` 这类格式
- 版本号只有一个来源：`package.json` 的 `version` 字段。其它地方（安装包名、界面显示、`latest.yml`）全部由它派生，不手改

### 库结构版本 ≠ App 版本

`library.json` 里的 `schemaVersion` 是**独立**的整数，只在改动数据结构时 +1。
改结构时必须：

1. `src/shared/types.ts` 里把 `SCHEMA_VERSION` +1
2. 在 `src/main/library.ts` 的 `MIGRATIONS` 里补一条 `目标版本 -> 迁移函数`
3. 在 CHANGELOG 的该版本下写一句「库结构升级到 v2，首次打开会自动迁移，迁移前自动备份为 library.json.bak」

迁移函数必须是**幂等且只向前**的：只写「从 vN 到 vN+1」，不写跨版本跳转。

## 2. 提交信息：Conventional Commits 1.0.0

格式：

```
<类型>(<范围>): <简短描述>

<可选正文：为什么这么改>

<可选脚注：BREAKING CHANGE / Closes #12>
```

### 类型表（只用这些）

| 类型 | 含义 | 是否出现在 CHANGELOG | 触发版本 |
| --- | --- | --- | --- |
| `feat` | 新功能 | ✅ 新增 | MINOR |
| `fix` | 修缺陷 | ✅ 修复 | PATCH |
| `perf` | 性能优化 | ✅ 变更 | PATCH |
| `refactor` | 重构（不改外部行为） | ❌ | — |
| `docs` | 文档 | ❌ | — |
| `style` | 格式（不影响逻辑） | ❌ | — |
| `test` | 测试 | ❌ | — |
| `build` | 构建/依赖 | ❌ | — |
| `ci` | CI 配置 | ❌ | — |
| `chore` | 杂项 | ❌ | — |
| `revert` | 回滚 | ✅ 移除 | PATCH |

### 范围（scope）建议取值

`lib` 库存储 · `media` 媒体 · `import` 导入 · `export` 分享包 · `ui` 界面 ·
`dup` 重复检测 · `updater` 更新 · `ext` 浏览器插件 · `build` 打包

### 示例

```
feat(import): 连号文件自动合并为一条记录

同一提示词跑出的 xxx_1.png / xxx_2.png 原本会生成两条记录，
现在按去掉尾号后的文件名归组，共用一条提示词。

Closes #7
```

```
fix(ui): 卡片内容溢出导致相邻行文字重叠

.card-info 改成固定高度 + overflow hidden，
行高常量 TEXT_H 与 CSS 高度必须保持一致（86px）。
```

```
feat(lib): 库结构升级到 v2，新增 assets.sha256 索引

BREAKING CHANGE: 首次打开会自动迁移旧库，迁移前备份为 library.json.bak。
```

**破坏性变更必须**写 `BREAKING CHANGE:` 脚注，且提交类型用 `feat` 或 `fix` 都可以，
但版本号必须升 MAJOR。

### 提交纪律

- 一个提交只做一件事。改了三个不相关的东西 → 拆三个提交
- 标题不超过 72 字符，动词开头，不加句号
- 不要写「update」「fix bug」「修改」这类无信息量的标题

## 3. Git 标签

- 格式：`vMAJOR.MINOR.PATCH`，**必须带 `v` 前缀**（`v1.0.0`）
- 注解标签（annotated），不是轻量标签：`git tag -a v1.0.0 -m "PromptPair 1.0.0"`
- 标签必须打在 `main` 分支的提交上
- **标签一旦推送就不许删改**。发错了版本 → 发更高的 PATCH 号修，不要重打 tag
  （重打会导致已经自动更新的用户错过更新或反复下载）
- 一次发布 = 一个 tag = 一个 GitHub Release

查看/校验：

```bash
git tag -n                       # 列出标签与说明
git describe --tags --always     # 当前所在位置
git show v1.0.0                  # 看标签指向的提交
```

---

## 4. CHANGELOG

遵循 Keep a Changelog 1.1.0，只用这六个小节：

`新增 Added` / `变更 Changed` / `弃用 Deprecated` / `移除 Removed` / `修复 Fixed` / `安全 Security`

规则：

- **写给人看，不写给机器看**：写「修复导入时同名标签会重复创建」，不写「fix tag bug」
- 面向使用者描述影响，不描述实现细节（实现细节放提交正文）
- 同一版本内按「影响面从大到小」排序，最重要的放最前
- `[未发布]` 一节始终存在，开发中的改动先写进去
- 发版时把 `[未发布]` 改名为 `[x.y.z] - YYYY-MM-DD`，再新开一个空的 `[未发布]`
- 不允许出现空版本（只有版本号没有任何条目）

## 5. 发布流程（标准动作，照做即可）

### 日常开发

```bash
git add -A
git commit -m "feat(import): 支持读取 ComfyUI 工作流"
git push
```

### 发一个修复版

```bash
npm version patch --no-git-tag-version   # 0.1.0 -> 0.1.1
# 手动把 CHANGELOG 的 [未发布] 改成 [0.1.1] - 今天日期，并新开 [未发布]
git add -A
git commit -m "chore(release): 0.1.1"
git tag -a v0.1.1 -m "PromptPair 0.1.1"
git push --follow-tags
```

推送 tag 后 GitHub Actions 自动：

1. `npm ci` → `typecheck` → `build`
2. `electron-builder --publish always` 生成 `PromptPair-Setup-x.y.z.exe` + `latest.yml`
3. 发布到 GitHub Releases

客户端在 8 秒后静默检查，发现新版本自动下载，下载完弹窗问是否重启安装。

### 发布检查清单

发布前逐条确认，缺一条就不发：

- [ ] `npm run typecheck` 与 `npm run build` 本地通过
- [ ] CHANGELOG 已更新，`[未发布]` 已改成正式版本号 + 日期
- [ ] `package.json` 的 `version` 与 CHANGELOG 顶部版本一致
- [ ] 库结构有变动时：`SCHEMA_VERSION` 已 +1 且补了迁移函数
- [ ] 手动跑一遍核心闭环：导入 → 打标 → 搜索 → 导出分享包 → 双击 index.html 能看
- [ ] 老库能正常打开（把上一版的库复制一份试）
- [ ] 标签格式正确（`v` 前缀、三位数字）

### 紧急回滚

不要 `git revert` 掉发布提交再重发同版本号。正确做法：

1. 找到问题提交，`git revert <sha>`
2. 升 PATCH 号发新版本（例如 1.0.1 → 1.0.2）
3. CHANGELOG 的该版本写「修复 1.0.1 引入的 XX 问题」

原因：自动更新按版本号单调递增判断，重发同版本号会让已经升级的用户收不到修复。

## 6. 分支策略

单人项目，用最简的**主干开发**：

- `main` 永远可构建、可发布
- 大改动开短分支 `feat/xxx`，完成后 squash 合并回 `main`
- 不设 `develop`、不设 `release/*`（没有并行维护多个大版本的需求）
- 需要同时维护两个大版本时（例如 1.x 与 2.x 并行），才引入 `release/1.x` 长期分支

---

## 7. 自动更新相关的硬性约束

这几条不遵守，自动更新会静默失效：

1. `electron-builder.yml` 的 `publish.owner` / `repo` 必须与真实仓库一致
2. GitHub Release 必须是**已发布**状态，草稿（draft）客户端看不到
3. Release 里必须包含 `latest.yml`（electron-builder 自动生成，不要手动删）
4. 安装包文件名不要手改（`latest.yml` 里写的是确切文件名）
5. 版本号必须递增，不能回退
6. 应用 `appId`（`com.promptpair.app`）不能改 —— 改了会被当成另一个软件，更新链断裂

---

## 8. 安装包与签名

- 当前未购买代码签名证书，安装时 Windows 会提示「未知发布者」，点「更多信息 → 仍要运行」即可
- 未来接入签名只需在 CI 里加两个环境变量（证书 base64 与密码），并删除 `electron-builder.yml` 中相关注释；**不影响版本与发布流程**
- 卸载**不会**删除素材库（默认在 `文档\PromptPair`），升级同理

## 9. 构建产物与本地目录规范

> 这一节是因为一次真实的混乱才加的：仓库里一度同时存在 `release/`、`rel/`、`rel2/` 三个产物目录，
> 还有一个手工改名成「旧包-0.1.0-已废弃-请勿安装.exe」的安装包。**问题不在技术，在流程。**

### 9.1 唯一的产物目录

| 目录 | 谁生成 | 是否入库 | 说明 |
| --- | --- | --- | --- |
| `out/` | `electron-vite build` | ❌ | 编译中间产物（main / preload / renderer 的 bundle） |
| `release/` | `electron-builder` | ❌ | **唯一的打包产物目录**，与 `electron-builder.yml` 的 `directories.output` 一致 |

除了这两个，任何 `dist/`、`build-out/`、`rel/`、`rel2/` 都属于违规产物。

### 9.2 硬性禁止：不许用 `--config.directories.output=xxx` 绕路

构建失败时（最常见的是产物被占用，报 `The process cannot access the file`），
**不许**换个输出目录重跑。绕一次就多一个目录，绕两次就没人知道哪个才是最新的。

正确动作是三步排查：

1. **看是不是程序还开着**（它可能正从产物目录里运行，锁住了 `app.asar`）：

   ```powershell
   Get-Process PromptPair -ErrorAction SilentlyContinue | Select-Object Id, Path
   ```

2. **关掉它**（只关本机的，别关别人的）：

   ```powershell
   Get-Process PromptPair -ErrorAction SilentlyContinue | Stop-Process -Force
   ```

3. **清理干净再重建**：

   ```bash
   npm run clean     # 删 release/ 与所有遗留目录，并报出还占着文件的具体路径
   npm run dist
   ```

`npm run clean` 删不掉时，说明有外部进程（杀毒、索引服务、还开着的程序）在占用。
先解决占用再重试，**依然不许换目录**。

#### 如果连 `npm run clean` 都被拦死

本机实测过一种极端情况，记录在这里省得下次重新排查：

- 现象：`release/`、`rel/` 里的 `app.asar` **删不掉也改不了名**，报 `SHARING_VIOLATION`；
  但同目录新建的文件能正常删，重启电脑后依旧。
- 定位：`handle64.exe <路径>` 查出句柄持有者 —— **是编辑器/宿主程序自己**
  （它做文件变更追踪时打开了这些文件，操作失败后没有关闭句柄）。
- 自锁：每次尝试删除都会让宿主再打开一次文件，于是永远删不掉。
- 解法：**完全退出宿主程序后**，再删。项目里留了一个双击即用的脚本：
  `scripts\清理构建残留.bat`（它会先检测宿主是否还在跑，在跑就拒绝执行并提示）。

> 排查工具：Sysinternals `handle64.exe`（不需要装，单文件）。
> 查谁占着某个文件：`handle64.exe -a "文件名" | findstr 关键字`。

**记一条纪律**：在这个项目里做清理，优先用 `git clean -xdf <目录>`
（git 走原生 unlink），不要用 `rm -rf` / `Remove-Item` —— 后者会被删除拦截层接管，
反而多一层占位。

### 9.3 产物命名：只允许工具自动生成

合法文件名只有 electron-builder 按模板生成的这一种：

```
PromptPair-Setup-<版本号>.exe
PromptPair-Setup-<版本号>.exe.blockmap
latest.yml
```

**禁止手工改名**，尤其禁止：

- ❌ `旧包-…-已废弃-请勿安装.exe`
- ❌ `…-最终版.exe`、`…-副本.exe`、`…-新版(2).exe`
- ❌ 任何中文名、空格、括号

两个理由：`latest.yml` 里写的是**确切文件名**，改名会让自动更新对不上；
而且"废弃"这种信息靠文件名传递本身就是错的 —— 废弃的包直接删就行。

### 9.4 坏包直接删，不留存

构建坏了、配置错了、版本发错了 —— **删掉**，然后：

- 要追溯某次发布 → 看 git tag + GitHub Releases（那才是权威记录）
- 要回滚 → 发一个更高的 PATCH 版本，不重发旧版本号

本地不留"历史安装包"。真想留，就上传到 Release，让它有条目、有校验、有版本号。

### 9.5 交付口径

| 来源 | 地位 |
| --- | --- |
| GitHub Releases | **唯一权威**，用户只应从这里下载 |
| 本地 `release/` | 便利副本，仅供本机测试；版本必须与某个 tag 完全一致 |

对外发链接一律指向 `releases/latest`，不发本地路径 —— 本地路径既不可追溯，
也可能是被改过的半成品。

### 9.6 构建产物永不入库

`.gitignore` 里 `out/`、`release/`、`dist/` 以及遗留的 `rel*/` 全部忽略。

> 真实事故：一次 `git add -A` 把 349 MB 的 `rel2/` 提进了暂存区，push 被中断才没推上去。
> 事后靠 `git reset --soft` + `git gc --prune=now` 把 `.git` 从 189 MB 清回 437 KB。
> 提交前用 `git status --short` 扫一眼，比事后清历史便宜得多。
