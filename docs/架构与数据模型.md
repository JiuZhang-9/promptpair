# 架构与数据模型

这份文档记录**为什么这样设计**。改代码前先读它，能避免拆掉承重墙。

---

## 一、第一性原则

做这个工具时，先问的是「素材的本质是什么」，而不是「参考哪个软件」。

生成式创作的资产不是"一堆图片"，而是：

> **一次输入（提示词 + 参数）→ 若干输出（图片/视频）**

由此推出三条不可动摇的设计：

| 原则 | 推论 |
| --- | --- |
| **配对是一等公民** | 数据模型必须是一对多（1 提示词 : N 产物），不能用「一条记录一张图」凑 |
| **元数据比文件更重要** | 文件是可再生的，提示词与参数是不可再生的 → 数据的可读性、可迁移性优先 |
| **库必须是自包含的** | 「打包带走」是核心诉求 → 媒体复制进库、用相对路径、单文件元数据 |

其余所有决定，都是这三条的推论。

## 二、数据模型

唯一事实来源：`src/shared/types.ts`。主进程与渲染层都从这里取类型。

```
LibraryData
├─ schemaVersion   库结构版本（与 App 版本无关）
├─ id / name      库标识
├─ entries[]      提示词记录（1 : N 的"1"）
│   ├─ title / positive / negative / note
│   ├─ rating 0-5 / favorite
│   ├─ collectionIds[]   多对多 → 集合
│   ├─ tagIds[]          多对多 → 标签
│   ├─ assetIds[]        一对多 → 产物（顺序即展示顺序）
│   ├─ params{model,seed,width,height,steps,cfg,sampler,reference,extra}
│   └─ source{platform,url,originalName,originalPath}
├─ assets[]       媒体文件（按内容寻址，全局唯一）
│   ├─ id          = sha256 前 24 位
│   ├─ sha256 / bytes / ext / kind(image|video)
│   ├─ relPath     media/ab/<sha>.png
│   ├─ thumbRel    thumbs/ab/<sha>.jpg
│   └─ phash       64bit 感知哈希（16 位十六进制）
├─ tagGroups[]    {name, color, order}
├─ tags[]         {name, groupId}   ← 颜色继承所属组
└─ collections[]  {name, color}
```

### 几个刻意的取舍

**为什么 `assetIds` 放在 entry 上，而不是给 asset 加 `entryId`？**
因为一条媒体理论上可以被多条记录复用（同一张图被两次不同的提示词迭代引用）。
用 `entry.assetIds` 表达，天然支持复用；渲染时反过来建一次索引即可。

**为什么标签颜色挂在组上，不挂在标签上？**
颜色是为了**扫读分组**，不是装饰。组内统一色，视觉上立刻能分出「风格类 / 题材类」。
标签级独立上色会让侧栏变成调色盘，反而更难读。

**为什么不存"来源文件夹"的绝对路径历史？**
只存 `originalPath` 作为追溯线索，**永不用于读取**。所有读取都走 `relPath`。
这样库搬走、原目录删掉，都不影响打开。

## 三、存储布局

```
<库根>/
├─ library.json         元数据（唯一写入点）
├─ library.json.bak     上一次保存的完整副本
├─ library.json.tmp     原子写中间文件（写完 rename）
├─ media/ab/<sha>.png   原始文件，按 sha 前两位分片
├─ thumbs/ab/<sha>.jpg  缩略图（512px 内，JPEG 82%）
└─ .incoming/           浏览器采集的临时落盘（即时清理）
```

### 为什么是 JSON 而不是 SQLite

这是本项目最值得解释的技术决策。

| 维度 | JSON（选用） | SQLite |
| --- | --- | --- |
| 构建可靠性 | ✅ 零原生依赖，`npm install` 即成功 | ❌ `better-sqlite3` 需要 node-gyp / VS Build Tools，Windows 上是最常见的构建失败源 |
| 可调试性 | ✅ 记事本能打开，用户能自己看、自己备份 | ❌ 需要工具 |
| 可迁移性 | ✅ 单个文件，随便拷 | ⚠️ 需要导出 |
| 万级性能 | ✅ 全量载入内存 + 索引，筛选 <5ms | ✅ |
| 十万级以上 | ⚠️ 内存占用上升 | ✅ |

对一个**个人素材库**（几千到几万条），JSON 的性能完全够用，而构建可靠性是零代码用户的生死线。
所以选择 JSON，并把所有读写收敛到 `Library` 类里 —— 未来真要换 SQLite，只改这一个文件。

### 原子写与备份

```
写 library.json.tmp  →  （若 library.json 存在）复制为 library.json.bak  →  rename(tmp, library.json)
```

`rename` 在同分区是原子操作，不会出现"写一半断电"导致半截 JSON 的情况。
读取失败时自动回退 `.bak`。

保存是**延迟 250ms 合并写**的（`touch()`），避免批量操作时反复写盘；退出前强制 `flush()`。

## 四、媒体管线

```
外部文件
   │  sha256（流式计算）
   ▼
库里已有同 sha？──是──▶ 直接复用 Asset，不复制
   │否
   ▼
复制到 media/ab/<sha>.<ext>
   │
   ├─ 缩略图：nativeImage.createThumbnailFromPath（系统解码器，视频也能抽帧）→ 失败回退 createFromPath + resize → JPEG
   └─ 感知哈希：缩放到 9×8 → 灰度差分 dHash → 16 位十六进制
```

**为什么用内容寻址（hash 文件名）？**
一次操作同时解决了三件事：去重、幂等、可校验。不需要额外的"是否已导入"判断表。

**为什么缩略图不用 sharp/ffmpeg？**
引入原生模块会破坏"零依赖构建"这条底线。Electron 自带的 `nativeImage` 已经能做缩放，
Windows 上的 `createThumbnailFromPath` 甚至直接调系统缩略图提供器，连视频封面都免费拿到。

**为什么渲染层用自定义协议 `ppmedia://` 而不是 `file://`？**
1. `file://` 在渲染层被 CSP 与安全策略针对，容易踩坑
2. 自定义协议可以集中做**路径白名单**（只允许访问库内文件），避免路径穿越
3. 可以自己实现 **Range 请求**，视频才能拖进度条

## 五、进程边界

```
┌─────────────── 主进程（Node 全权限） ───────────────┐
│  library / media / importer / exporter / updater    │
│  capture(127.0.0.1)   protocol(ppmedia)             │
└──────────────▲──────────────────────────────────────┘
               │  ipcMain.handle（显式白名单，共 ~30 个通道）
┌──────────────┴──────────────────────────────────────┐
│  preload：contextBridge.exposeInMainWorld('pp', …)  │
└──────────────▲──────────────────────────────────────┘
               │  window.pp.xxx()
┌──────────────┴──────────────────────────────────────┐
│  渲染层（React，无 Node，contextIsolation: true）    │
└─────────────────────────────────────────────────────┘
```

铁律：

- 渲染层**永远**拿不到 `require`、`fs`、`path`
- 新增能力必须三处同步：`main/ipc.ts` 加 handle → `preload/index.ts` 加方法 → `preload/index.d.ts` 加类型
- 事件订阅只允许 `preload/index.ts` 里那个 `allowed` 集合内的通道，其它一律抛错

### 状态同步策略

不做"每次变更推送全量库"（几万条时 JSON 序列化会很贵）。分两种：

- **单条变更**（保存/删除/批量）：主进程返回变更结果，渲染层 `refresh()` 拉全量快照 → 简单可靠，操作频率低
- **高频筛选/搜索**：完全在渲染层内存里算（`selectEntries`），不碰主进程

代价是每次 refresh 都走一次全量 IPC。在当前量级（十万条以内，单次约几十 MB 上限）可以接受；
若未来库规模继续变大，应改为增量补丁。

## 六、导入规则引擎

规则集中在 `src/main/importer.ts`，都是"可解释、可关掉"的：

| 规则 | 实现位置 | 开关 |
| --- | --- | --- |
| 连号文件合并 | `stemKey()` | `autoGroupByStem` |
| 文件夹名→标签 | `tagsFromPath()` | `autoTagFromFolder` |
| 自动创建标签 | `ensureTag` 调用点 | `autoCreateTags` |
| 读旁车文件 | `readSidecar()` / `readSidecarByStem()` | `autoReadSidecar` |
| 平台识别 | `detectPlatform()` | 恒开（只影响展示） |

### `stemKey` 的归组规则

```
赛博朋克女孩_1.png  →  赛博朋克女孩
赛博朋克女孩_2.png  →  赛博朋克女孩
cyber_girl (1).jpg →  cyber_girl
cyber_girl-02.jpg  →  cyber_girl
xxx_seed12345.png  →  xxx
xxx_hd.png         →  xxx
```

只去掉**尾部**的序号/修饰，不动词干 —— 防止 `v2_角色` 这类名字被误伤。

### `tagsFromPath` 的三级规则

1. 整名命中已有标签 → 直接用，不拆
2. 名字含某个**标签组名** → 其余部分作为标签，归入该组
   （`风格_赛博朋克` → 标签「赛博朋克」入组「风格」）
3. 其它 → 按分隔符拆成多个标签（中文允许 `_` 作分隔，英文只用 `、,，|`）

同时有一张**容器名单**（`CONTAINER_FOLDER`）：`下载 / 桌面 / 文档 / 图片 / 新建文件夹 / output` 等
不会被当成标签 —— 否则从下载目录导一次，全库都会打上「Downloads」。

## 七、分享包格式（`.promptpack`）

一个 ZIP，**故意做成开放格式**：

```
manifest.json      {magic, formatVersion, appVersion, library, counts, hasMedia, entry}
data/prompts.json  全部结构化数据（标签/集合按名字引用，不依赖本地 ID）
index.html         自包含浏览页（内联 CSS/JS，数据以 JSON 内嵌）
README.txt         给收包人的说明
media/…            原始文件
thumbs/…           缩略图
```

设计要点：

- **按名字而非 ID 引用**标签与集合 → 导入到别的库时能自动对齐，不会产生孤儿 ID
- **`formatVersion` 独立于 App 版本** → 未来格式演进不影响老包可读
- **`index.html` 零外部依赖** → 双击即开，不需要联网、不需要装任何东西
- 导出用**流式写入**（`fflate` 的 `ZipPassThrough`），几百 MB 的包不会炸内存
- 导入用**流式解包**（`Unzip` + 逐文件写盘），并做了路径穿越防护（拒绝含 `..` 的条目）

## 八、重复检测

两级：

| 层级 | 方法 | 成本 |
| --- | --- | --- |
| 精确重复 | sha256 内容寻址 | 0（入库时天然完成） |
| 近似重复 | dHash 64bit + 汉明距离 + 并查集聚类 | O(n²)，2000 张约 200 万次比较，<50ms |

阈值默认 6（可 0–16 调）。并查集让"链式相似"（A≈B, B≈C）归为同一组，而不是两两成对。
清理时保留组内**体积最大**的，其余从磁盘删除并摘掉所有引用。

## 九、自动更新

```
electron-builder --publish always
        │
        ├──▶ GitHub Releases: PromptPair-Setup-x.y.z.exe + latest.yml + .blockmap
        │
客户端 electron-updater
        ├── 启动 8s 后检查，之后每 4h
        ├── 自动下载（差量，靠 blockmap）
        └── 下载完成弹窗 → 用户确认 → quitAndInstall
```

必须成立的硬约束（违反会静默失效）：

1. `publish.owner/repo` 与真实仓库一致（用 `scripts/set-repo.mjs` 写入）
2. Release 必须是**已发布**状态，草稿客户端读不到
3. 版本号单调递增
4. `appId` 不可更改 —— 改了等于换了个软件，更新链断裂

## 十、扩展点

### 想加一个字段（例如"作者"）

1. `src/shared/types.ts`：`PromptEntry` 加字段，`SCHEMA_VERSION` +1
2. `src/main/library.ts`：`MIGRATIONS` 补 `{ [新版本]: d => { 给旧数据补默认值; return d } }`
3. `upsertEntry` 里带上新字段
4. 界面：编辑弹窗加输入框、详情面板加展示
5. `docs/` 补一句；CHANGELOG 记一条 `feat(lib):` + `BREAKING CHANGE` 说明

### 想加一条导入规则

1. `src/main/importer.ts` 里加函数，**必须**在 `ImportOptions` 或 `AppConfig` 里给开关
2. 规则要幂等：同一批文件重复导入结果一致
3. `scripts/verify-import.cjs` 补一条断言

### 想换存储后端

只改 `src/main/library.ts` 的 `Library` 类（load/flush/CRUD），其余模块只依赖它的方法签名。

## 十一、已知技术债

按优先级排列，都是**有意识的延后**，不是遗漏：

1. **状态刷新是全量的** —— 万级以上应改增量补丁（见第五节）
2. **视频拿不到原始分辨率** —— `createThumbnailFromPath` 只给缩略图尺寸；要精确值需引入 ffprobe
3. **重复检测是 O(n²)** —— 十万张图需要分桶（按 phash 前缀）预筛
4. **无端到端 UI 测试** —— 目前靠 `scripts/screenshot.cjs` 视觉验收 + 两个管线断言脚本
5. **单库同时只能开一个实例** —— 有意为之（避免两进程抢写同一份 library.json）
