# 路线图与待办

> 这份文件回答一个问题：**接下来做什么，为什么是它，做完算不算成功。**
> 每条都带验收标准，没写验收标准的不进计划。

---

## 判断标准（先定规则，再排优先级）

任何新需求先过这三道闸，过不了的直接不做：

1. **是否强化主线**——配对（1 提示词 : N 产物）、元数据（标签/参数）、可搬运（自带库 + 分享包）。三条之外的都属于"另一个产品"。
2. **是否减少零代码用户的操作次数**——同样的事，能不能少点两下、少填一个框。
3. **是否会破坏"零原生依赖 / 库自包含"两条硬约束**——会的话，除非收益极大，否则换成别的做法。

优先级定义：

- **P0**：不做就会让人放弃使用（阻断核心闭环）
- **P1**：不做会明显降低日常效率（每天都要用的动作还别扭）
- **P2**：锦上添花（有了更好，没有也能过）

## P1 · 效率级（下一轮要做）

### 1. AI 辅助打标 —— 0.3.0

**问题**：存量素材几千张时，手工打标是不可完成的任务。规则引擎只能覆盖"文件夹名规范"的那部分。

**方案**：
- 设置里填一个 OpenAI 兼容的接口（Base URL + Key + 模型名），**可选**，不填就完全离线
- 选中一批记录 →「AI 打标」→ 把缩略图 + 现有提示词发给视觉模型 → 返回候选标签
- **必须先给出候选再让用户确认**，不做静默写入。标签是用户的心智资产，不能脏
- 优先复用已有标签（把现有标签列表一起发给模型，要求优先从中选），避免标签爆炸

**验收**：
- 20 张图批量打标，用户接受率 ≥ 70%
- 已有标签复用率 ≥ 60%（新造标签数 ≤ 8）
- 无 API Key 时功能整体消失，不影响任何现有流程

**成本**：中。主要难度在提示词工程与结果去重，不在代码。

---

### 2. 标签治理 —— 0.3.0

**问题**：自动打标跑久了必然出现「赛博朋克 / 赛博 / cyberpunk」三个同义标签。

**方案**：
- 设置 →「标签管理」：列出所有标签，按使用数排序，可批量重命名、合并、删除
- 合并：把 B 的所有引用替换成 A，然后删除 B
- 检测近似重复（编辑距离 ≤ 2、包含关系、大小写/空格差异）给出合并建议

**验收**：
- 合并后引用数正确，无孤儿标签
- 一次操作可处理 ≥ 50 个标签而不卡顿

**成本**：低。

---

### 3. 快捷键全覆盖 —— 0.3.0

**问题**：现在只有搜索/新建/删除/保存。批量打标靠鼠标，效率上不去。

**方案**（照抄成熟工具的心智，不发明）：

| 键 | 动作 |
| --- | --- |
| `J` / `K` 或 `↑` `↓` | 上下移动焦点（不改选中） |
| `Space` | 切换当前项选中 |
| `1`–`5` | 给选中的打 N 星 |
| `F` | 收藏 |
| `E` | 编辑 |
| `T` | 打开标签面板 |
| `Ctrl+A` | 全选当前筛选结果 |
| `Ctrl+Shift+E` | 导出选中 |
| `?` | 快捷键帮助浮层 |

**验收**：不看鼠标能完成"筛选 → 全选 → 加标签 → 导出"全流程。

**成本**：低（但要想清楚焦点模型，别做出反直觉的行为）。

---

### 4. 保存筛选视图 —— 0.5.0

**问题**：常用的组合（"标签=赛博朋克 且 评分≥4 且 未归集合"）每次都要重设。

**方案**：筛选栏右侧「存为视图」，存进库（`library.json` 加 `views[]`），侧栏可一键切换。视图是本地数据，进分享包。

**验收**：视图能随库一起搬走，换电脑后仍在。

**成本**：低-中（要动 schema，记得升 `SCHEMA_VERSION`）。

## P2 · 增强级（有余力再做）

### 5. 视频能力 —— 0.4.0

- 现在：靠系统缩略图抽一帧，能看不能用
- 目标：库内播放（已有 `<video>` + Range 支持，基本可用）、显示真实时长与分辨率、hover 预览 3 秒
- **代价**：精确时长/分辨率要 ffprobe，会给安装包加 ~50 MB，且引入原生二进制
- **替代方案先试**：Windows 上读文件属性（Shell API）拿时长，避免打包 ffmpeg。若可行就不引 ffmpeg

### 6. 导出静态站点 —— 0.6.0

把 `.promptpack` 里的 `index.html` 再往前推一步：一键导出可直接上传到任意静态托管的网站（含缩略图、搜索、标签筛选）。适合发教程、卖预设包。

### 7. 相似图搜索

点一张图 →「找相似的」→ 用现有 dHash 做全库排序。不需要向量库，纯色块图会有误判，但对"同一个角色换个角度"很有效。

### 8. 多库切换

现在只支持单库 + 集合。若用户真的需要"客户A 一个库、个人一个库"，再加库切换器（数据层已支持，只是 UI 未开）。

### 9. 崩溃与错误上报

本地记录错误日志到 `%APPDATA%/PromptPair/logs`，设置页可一键导出。**不做自动上报**（本地优先原则）。

## 明确不做

写下来是为了以后不被反复讨论：

| 不做 | 原因 |
| --- | --- |
| 云端同步 / 账号体系 | 违背"本地优先、库自包含"。用户要同步就自己放网盘 |
| 内置 AI 生成 | 本工具管"已产出的资产"，不负责生成。接生成器只会变成另一个产品 |
| 团队协作 / 权限 | 个人工具。多人共享走"导出分享包"这条路够了 |
| 移动端 | 素材在电脑上产生，管理也在电脑上 |
| 用数据库替换 JSON | 见 `docs/架构与数据模型.md` 第三节：构建可靠性 > 极限性能 |
| 自动上传到图床 / 社交平台 | 同上，越界 |

## 技术债清单（与功能并行）

这些不产生新功能，但不还会越来越贵。按"什么时候必须还"排序：

| 债 | 触发条件 | 还法 |
| --- | --- | --- |
| 状态刷新是全量 IPC | 单库 > 2 万条 | 改增量补丁 |
| 重复检测 O(n²) | 单库 > 5 万张图 | 按 phash 前缀分桶预筛 |
| 没有 E2E 测试 | 每次改动都要手动回归 | 用 Playwright 驱动 `out/main`，覆盖导入/导出/打标三条主链路 |
| 分享包全量导出 | 用户频繁导出大库 | 增量包（只含差异），依赖归档格式版本升级 |
| 视频分辨率不准 | 0.4.0 做视频时 | 见 P2-5 的替代方案 |

---

## 怎么推进（每次发版的固定动作）

1. 从本文档挑一条 **P1**，确认验收标准没变
2. 开分支 `feat/xxx`，做完 squash 合并
3. 更新 CHANGELOG 的 `[未发布]`
4. 按 `docs/发布规范.md` 走发布流程（`npm version` → tag → push）
5. 发布后回本文档勾掉对应项，把新发现的问题补进来

> 规则：**一次发版只做一个主题**。0.3.0 就是"打得快"，不要混进视频功能。
